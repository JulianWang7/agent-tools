## 1. 文档说明

### 1.1 编写目的

本规范规定用例图、系统架构图、组件图、时序图在编制、评审与维护时应遵守的统一要求。

**应当：** 将每张图视为可评审工件；材料不足处标注「待确认」「TBD」或「基于当前材料推断」。
**不应：** 用未验证细节填充空白；混用多套符号语义而无图例。

**出图前置决策**：仅当图示能明显提升内容理解效率时才生成。不得先生成图片再反向编造用途。

### 1.2 适用范围

适用于四类图（用例图、系统架构图、组件图、时序图）的新建、修订与归档，以及本规范涵盖的类图、状态图、活动图、部署图等 UML 扩展图种。不适用于具体项目业务正文、源代码级 API 手册及无关组织流程。

### 1.3 适用读者

- 架构师/设计人员
- 开发工程师
- 测试工程师
- 评审与质量人员
- LLM/自动化制图工具使用者

### 1.4 术语与标注

| 术语 | 含义 |
|------|------|
| 动词＋业务对象 | 用例命名格式，如「提交订单」 |
| 待确认/TBD | 见 §2.8 与 §18 |
| 两件套 | 可编辑源文件 + 渲染 SVG（见 §13） |
| PlantUML | UML 图种首选工具，基于文本的 UML 渲染引擎 |
| Mermaid | 轻量级 Markdown 内嵌图表工具，仅限草稿 |

### 1.5 与工程图示的关系

可扩展 UML 元素，但线型、箭头、颜色须在图例自洽。

### 1.6 出图前置约束

在启动制图前，须逐项确认：

1. 先确认图类型
2. → 确认图的主题和边界
3. → 确认节点清单（须有来源依据或「待确认」标记）
4. → 确认关系清单（每条连线可解释语义；无法确认的关系不得自行补全）
5. → 选择标准 UML 元素（相同类型节点复用统一样式）
6. → 统一布局和样式
7. → 检查语义
8. → 检查视觉质量
9. → 完成后对照 §16 检查清单

### 1.7 参考依据

- [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/About-UML)
- [C4 Model Notation](https://c4model.com/diagrams/notation)
- [PlantUML Theme](https://plantuml.com/theme)

## 2. UML 图总体原则

### 2.1 准确性原则

图示须与已批准需求、设计决策、接口说明或可核验事实一致。
**应当：** 变更时同步更新或标注材料日期。
**不应：** 删减关键分支或冒充已定模块。
**反例：** 无需求依据的「消息队列」模块。

### 2.2 一致性原则

命名、箭头、颜色在文档集内一致；关联图实体可对应。
**不应：** 用例写「客户」、架构写「用户」、组件写「Client」无对照。

### 2.3 可读性原则

布局清晰、对齐、少交叉；有标题与图例。

### 2.4 适度抽象原则

同图层级一致；上层概括、下层细化。

### 2.5 单图单主题原则

一图一评审焦点；过大则拆图并编号关联。

### 2.6 图文一致原则

符号、图例、文字描述同义。

### 2.7 可追溯原则

元素可映射需求/接口/组件；评审可定位。

### 2.8 禁止虚构原则

不得无材料绘制参与者、用例、组件、消息。
**应当：** 缺口用 TBD 或清单列出。

### 2.9 图示内容设计约束

以下为 B 文档补充的工程约束，与 §2.1～§2.8 互不替代：

- 节点名明确，文字不超两行
- 不得放大段正文/代码入节点
- 同层节点尺寸一致
- 主流程/异常/返回/依赖清晰区分
- 连线有明确方向
- 禁止连线重合
- 避免大量交叉
- 禁止节点重叠
- 模块多时先分组
- 复杂内容拆子图
- 不混用图种语义
- 图示与源码一致

## 3. 图示选型规范

### 3.0 工具选型总表

UML 图种默认优先使用 PlantUML；当 PlantUML 难以表达，或任务明确要求精细手工排版时，第二选择为 Draw.io MCP。切换工具前须记录回退理由。

| 图种 | 首选工具 | 源文件 | Draw.io MCP | 说明 |
|------|----------|--------|---------|------|
| **时序图** | **PlantUML** | `.puml` | 备选 | 回退时执行 §9.24 的严格目视检查 |
| **用例图** | **PlantUML** | `.puml` | 备选 | PlantUML 难以满足精细排版时使用 |
| **类图** | **PlantUML** | `.puml` | 备选 | PlantUML 难以满足精细排版时使用 |
| **状态图** | **PlantUML** | `.puml` | 备选 | PlantUML 难以满足精细排版时使用 |
| **活动图** | **PlantUML** | `.puml` | 备选 | PlantUML 难以满足精细排版时使用 |
| **组件图** | **PlantUML** | `.puml` | 备选 | 需手工微调复杂接口时可使用 |
| **部署图** | **PlantUML** | `.puml` | 备选 | 需手工微调复杂拓扑时可使用 |
| **系统/分层架构图** | **PlantUML** | `.puml` | 备选 | 需精细布局时可使用 |
| 多列每日任务流程图 | Draw.io MCP（泳道） | `.drawio` | **首选** | 非 UML 工程流程图 |
| 简单流程/决策图（≤15 节点） | Mermaid | `.mmd` | — | 节点拥挤时升级 PlantUML |

**一句话规则：正式 UML 图先用 PlantUML；PlantUML 难以表达或需要精细手工排版时，再用 Draw.io MCP，并记录回退理由。**

各工具的详细使用约束见 §10。

### 3.1 用例图的适用场景

界定系统边界、参与者、对外能力；适合范围与测试划分。
**不宜：** 表达内部调用顺序或寄存器级流程。

### 3.2 系统架构图的适用场景

表达分层/分域、子系统关系、数据流/控制流/调用方向。
**应当：** 标明流向含义。

### 3.3 组件图的适用场景

表达组件划分、提供/需求接口、依赖、事件与回调。
**不宜：** 单独承担复杂并发时序。

### 3.4 时序图的适用场景

表达生命线间消息顺序、同步/异步、返回与组合片段。

### 3.5 四类图之间的关系

推荐链：用例（范围）→ 架构（结构）→ 组件（接口）→ 时序（行为）。
**应当：** 上层引用下层编号，避免矛盾。

### 3.6 常见选型错误

**反例：** 用架构图替代时序表达分支；用用例图罗列内部模块；组件图与时序依赖方向相反。

## 4. 统一命名规范

### 4.1 图文件命名

文件名宜含图种、主题、编号与版本，如 `用例-登录-图6-1_v1.0.drawio`。
**不应：** 仅用「未命名」「diagram1」。

### 4.2 图标题与编号

标题与正文编号一致，格式 `图 {章}-{序}`。

### 4.3 用例命名

采用**动词＋业务对象**；如「提交订单」「查询设备状态」。
**不应：** 名词化模块名冒充用例。

### 4.4 参与者命名

使用稳定业务角色或外部系统名。

### 4.5 组件命名

体现职责，可与构建单元映射。

### 4.6 接口命名

名词或名词短语；操作在时序消息体现。

### 4.7 消息与事件命名

时序消息用动词短语；异步宜具事件语义。

### 4.8 分层与部署命名

层名与组织已批准分层表一致。

### 4.9 待确认元素命名

后缀 `（待确认）`、`（TBD）`、`（推断）`。

### 4.10 中英文与缩略语规范

同一图主语言择一；首次出现「全称（缩写）」。
**不应：** 同一组件中英文随机切换无对照。

## 5. 统一视觉规范

### 5.1 页面方向

默认横向（左→右）布局；纵向仅当分层自上而下更清晰时采用，须在图注说明。

### 5.2 活动图/流程图方向约束

活动图/流程图优先竖向布局（自上而下），阶段名用右侧注释标注。横向泳道会导致图形向右膨胀——当阶段数 ≥ 4 或单阶段内容超过 2 个节点时，成品通常过宽不便查阅。

**规则：**
1. 主流程自上而下，每个 `note right` 标注其上方动作所属的阶段；
2. 阶段名加粗（`**① 阶段名**`）以区别于正文；
3. 阶段说明控制在 2～3 行，长文拆入正文不在图中展开；
4. note 只写阶段名 + 一句话结论，禁止重复主流程中已有的操作细节。

完整代码模板见 §20.6。

### 5.3 PlantUML 布局方向控制

| 关键字 | 方向 | 适用 |
|--------|------|------|
| 默认 | 从上到下 | 时序图、状态图 |
| `left to right direction` | 从左到右 | 架构图、分层图、组件图 |

### 5.4 画布与边距

保留足够边距放置标题与图例；避免元素贴边裁剪。

### 5.5 字体规范

| 用途 | 字体（优先级） |
|------|----------------|
| 中文 | 微软雅黑、Noto Sans CJK SC |
| 英文数字 | Arial |
| 等宽 | Consolas |

### 5.6 字号层级

| 元素 | 建议字号(pt) |
|------|-------------|
| 图标题 | 14–16 |
| 分区标题 | 12–13 |
| 主标签 | 11–12 |
| 图例/说明 | 9–10 |
| 时序消息 | 10–11 |

### 5.7 线宽与线型

| 语义 | 线型 |
|------|------|
| 主调用/主数据流 | 实线 1.5–2pt |
| 依赖/可选 | 虚线 1pt |
| 返回 | 虚线开放箭头 |
| 待确认 | 点划线+标注 |

### 5.8 颜色语义总则

颜色表意且灰度可区分；禁止仅靠颜色传达唯一信息。UML 图默认近单色或低饱和线框风格。颜色不代替 UML 图形语义。

### 5.9 UML 语义配色（Draw.io / 通用）

本配色表用于按业务语义区分元素角色：

| 语义 | 填充 | 边框 |
|------|------|------|
| 本系统 | #E3F2FD | #1565C0 |
| 外部系统 | #FFF3E0 | #EF6C00 |
| 应用组件 | #E8F5E9 | #2E7D32 |
| 基础设施 | #ECEFF1 | #546E7A |
| 接口 | #F3E5F5 | #6A1B9A |
| 待确认 | #FFFDE7 | #F9A825 |
| 异常路径 | #FFEBEE | #C62828 |

### 5.10 PlantUML 线框风格

PlantUML 渲染时推荐以下配色，用于「近单色线框」风格：

**默认线框风格：**

```text
画布/节点背景：#FFFFFF  分组背景：#F5F6F7
主要文字：#202124  次要文字：#5F6368
节点边框/连线：#70757A  强调色：#3F6F8F
```

**现代架构线框风格：**

```text
内部核心：背景 #EAF2F8 / 边框 #3D6D8E / 文字 #1F3442
外部元素：背景 #F2F3F5 / 边框 #8B949E / 文字 #4B5563
当前重点：背景 #FFF4D6 / 边框 #B7791F / 文字 #5F3B00
```

### 5.11 状态语义色

仅用于状态机/测试/CI-CD/异常/排查流程：

| 语义 | 填充 | 边框 |
|------|------|------|
| 正常 | #E8F5E9 | #3E7B4B |
| 警告 | #FFF4D6 | #B7791F |
| 错误 | #FCE8E6 | #B6453D |

**禁止**用于普通类图/组件图/架构图。

### 5.12 PlantUML 主题选择

所有 PlantUML UML 图种统一使用 `!theme materia-outline`，各图种模板见 §20。

同类图必须保持一致。

### 5.13 PlantUML style 用法（1.2022+）

用 `<style>` 块替代 `skinparam`。

**语法要求（实测必须遵守，否则渲染失败）：**

1. 每个属性**单独一行**，行尾用**分号** `;` 结尾；
2. **禁止**在同一行用空格分隔多个属性；
3. 选择器用小写元素类型名（`diagram`、`rectangle`、`package`、`arrow` 等）。

正确写法：

```plantuml
<style>
diagram {
  FontName "Noto Sans CJK SC";
  FontSize 13;
}
rectangle {
  BackGroundColor #EAF2F8;
  BorderColor #3D6D8E;
  FontColor #1F3442;
  RoundCorner 8;
}
package {
  BackGroundColor #F5F6F7;
  BorderColor #70757A;
  FontStyle bold;
}
arrow {
  Color #70757A;
  FontSize 11;
}
</style>
```

**禁止**使用 `skinparam`。**禁止**单行多属性空格分隔写法如 `diagram { FontName "..." FontSize 13 }`。

### 5.14 图例与标题

使用颜色/虚线/特殊边框时必须提供图例；灰度可理解；不仅靠红绿区分。非标准符号超过两种须附图例。

禁止样式：
- 彩虹配色
- 每模块一色
- 高饱和荧光色
- 渐变、发光、立体、厚重阴影
- 卡通图标
- 深色底白字

### 5.15 各图种视觉要素速查

| 图种 | 视觉要点 |
|------|----------|
| 用例图 | 参与者样式统一；用例椭圆与边界配色可区分 |
| 架构图 | 分层带清晰；跨层连线尽量正交 |
| 组件图 | 提供/需求接口符号成对；圆角一致 |
| 时序图 | 生命线对齐；激活条覆盖调用区间 |

### 5.16 对齐与导出

导出 SVG 时检查文字可读；保留可编辑源文件。

### 5.17 复杂图拆分原则

消息/用例/组件过多时按场景、域或层拆图，用编号串联。
**反例：** 单图 50+ 消息仍不拆分。

## 13. 源文件与渲染文件管理

每张正式图必须保留：源文件 + SVG。

### 13.1 目录结构

```text
docs/diagrams/
├── plantuml/
│   ├── source/          # .puml 源文件（UML 图种统一放此）
│   ├── rendered/        # 渲染产物 SVG
│   └── theme/           # 共享主题文件
├── drawio/
│   ├── source/          # .drawio 源文件（仅 draw.io 专属图）
│   └── rendered/        # 渲染产物 SVG
├── mermaid/             # 草稿（不正式交付）
└── d2/                  # 默认不使用
```

### 13.2 PlantUML 源文件归档

- `.puml` 放 `docs/diagrams/plantuml/source/`
- 渲染 SVG 放 `docs/diagrams/plantuml/rendered/`

### 13.3 Draw.io 源文件归档

- `.drawio` 放 `docs/diagrams/drawio/source/`
- 渲染 SVG 放 `docs/diagrams/drawio/rendered/`

### 13.4 常规图片

非程序生成的一般图片（截图、照片等）沿用 `docs/images/` 路径。

### 13.5 两件套原则

每个正式图示**应当**同时保留源文件 + SVG。源图经人工调整后**必须**重新导出 SVG，**不应**仅替换源文件而不更新导出件。

## 14. Markdown 引用约束

图片只引用 `.svg/.png/.jpg/.jpeg/.webp`，不引用 `.drawio/.puml/.d2/.mmd`。

- 路径相对当前 Markdown，禁止绝对路径
- 不同时设宽高
- 图号、图题、源文件链接完整

**反例：**

```markdown
<!-- 错误：引用源文件 -->
![架构图](docs/diagrams/plantuml/source/arch.puml)
<!-- 错误：绝对路径 -->
![架构图](C:/Users/xxx/docs/images/arch.svg)
<!-- 正确 -->
![图 7-1 系统分层架构](docs/images/arch.svg)
```
